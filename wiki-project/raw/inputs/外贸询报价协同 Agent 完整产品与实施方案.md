# 2 目标用户与业务切口

**一句话定位：业务员用中文整理买家需求，系统根据真实商品与企业知识生成可审核的海外报价；买家改需求时，自动说明价格、交期、合规和采购任务受到什么影响。**

首个用户画像：有稳定产品目录、通过 RFQ 或邮件接询盘、报价依赖 Excel 与同事沟通的中小出口企业。主要使用者为业务员；协作者为报价主管、采购与知识维护人员。先服务一个商家实例，避免把多租户 SaaS 建设拖进比赛范围。

演示选用「成人定制 T 恤出口德国」作为一个可执行假设：30 个演示 SKU，英语与德语买家产出，中文内部任务，覆盖 RFQ 首轮回复及邮件正式报价两个场景。这个品类用于让商品规格、纤维成分、数量阶梯与包装变更都能展示出来；如果拿到其他品类的真实商家数据，应以数据质量为依据整体替换演示品类和规则，不能沿用不适用的校验。

| 当前业务问题 | 本项目行为 | 可观察价值 |
| - | - | - |
| 询盘信息缺失，反复追问 | 提取需求、列出缺项、生成一次性澄清问题 | 减少往返轮次 |
| 报价查目录、历史单和问采购耗时 | 联合检索结构化商品与有来源知识 | 缩短首份可审核报价用时 |
| 买家改数量或包装后漏改条款 | 建立字段依赖并生成版本差异与复核任务 | 减少金额、交期和文本不一致 |
| 英文、德文和内部说明各写一遍 | 从同一份事实快照生成不同岗位与场景输出 | 降低多版本内容漂移 |
| 企业经验散落在文件中 | 形成带来源、有效期和责任人的 Wiki | 让知识能被检索、校正和复用 |

本项目不把「AI 能写报价」作为独有创新。可展示的区别是：每个关键结论有来源；每次变更有影响范围；每份对外产出有对应版本；待确认事项能交给明确岗位处理。

# 4 工作流一 从询盘到可审核报价

**触发：** 业务员粘贴 RFQ／邮件，或上传文本附件，并选择市场、输出语言和业务场景。MVP 采用手动导入，避免未经授权的平台抓取。

**参与岗位：** 业务员、报价主管；必要时采购确认交期和成本。

| 步骤 | 处理逻辑 | 产出／进入下一步的条件 |
| - | - | - |
| 1 理解需求 | 提取买家自述、产品、材质、数量、单位、包装、目的地、时间与贸易条件 | 结构化 Inquiry；附原文位置与缺失字段 |
| 2 查数据与知识 | 商品检索获取候选；Wiki 获取业务流程、已批准条款和市场知识 | 商品候选及带引用的相关知识 |
| 3 澄清关键缺口 | 对影响选品、价格和承诺的缺项提问 | 材质、交期或交货责任不明确时不自动假设 |
| 4 计算草稿 | 使用确定的价格版本、数量阶梯、成本项和币种计算 | 报价快照及计算依据；缺成本可生成待定草稿 |
| 5 本地化表达 | 根据 RFQ 或正式邮件模板生成目标语言内容 | 数量、金额、材料等来自同一结构化快照 |
| 6 规则校验 | 检查合同字段与选定市场规则 | 通过、提醒、阻断或待核实，附原因和依据 |
| 7 人员复核 | 业务员修订，主管确认价格例外等 | 可导出报价 PDF；保留审核人与版本 |

**对外输出：** RFQ 简短回复、正式报价正文、报价 PDF。**内部输出：** 中文报价摘要、待澄清问题、采购确认任务、风险清单。

关键约束：没有证据不能生成「已认证」「库存充足」「保证按期交付」等事实承诺；PDF 中存在价格或条款缺口时显著标记为草稿。审核、导出、标记已发送是不同动作；MVP 不把下载 PDF 自动当作已发给买家。

# 5 工作流二 需求变更与跨岗位复核

**触发：** 买家变更需求，业务员输入例如「数量减半，增加礼盒，希望提前交货，生成德文版」。

系统提取变化字段，与当前已保存版本比较，沿依赖关系重新计算和生成：

- 数量 → 数量阶梯、MOQ、单价、总额、生产安排。

- 材料 → SKU 资格、成分描述、成本、相关知识与规则。

- 包装 → 包装费用、尺寸重量与采购任务；运费未知则提示待确认。

- 交期 → 供应商确认、报价有效条件与对外承诺。

- 贸易条件 → 责任范围、费用是否包含、指定地点与对应条款。

- 语言／场景 → 文案与版式；不修改已经确认的业务事实。

**产出四件套：** 报价新版本、前后差异表、目标语言修订回复、中文采购／主管任务卡。任务卡包含问题、证据、责任岗位和待确认字段；不能只有笼统的「请处理」。

报价建议状态为：草稿、待澄清、待内部确认、待审核、已审核、已发送、已替代。后续版本不覆盖已发送版本；接受过的报价变更要走明确修订确认。并发写入携带 expectedRevision，过期修改提示刷新，避免业务员与采购互相覆盖。

**与知识库的联动：** 如果一条已批准的供货知识更新，系统依据引用关系找出受影响的未完成报价并创建复核任务。已发送单据保留当时快照，系统提示其可能受影响，由负责人决定是否通知买家。

# 6 演示数据与两轮对话

以下全部是拟造的演示数据，需在界面标记「演示商家／演示供应商」，不冒充真实采购价格、客户或法规结论。

| 对象 | 演示设定 | 作用 |
| - | - | - |
| SKU A | 成人 T 恤，95% 棉＋5% 氨纶，常规包装 | 制造「100% cotton」文案冲突的检查点 |
| SKU B | 成人 T 恤，100% 棉，常规包装 | 提供有数据依据的替代候选 |
| 成本表 | 每个 SKU 有不同数量档位、币种、生效版本 | 展示减量后不能机械减半总价 |
| 包装表 | 常规包装已确认，礼盒需补充供应商报价 | 展示缺成本时不虚构价格 |
| 供货确认 | 常规方案 30 天；20 天未获确认 | 展示交期承诺的边界 |
| 企业规则 | 已批准付款模板、最低内部毛利阈值、例外审批人 | 展示合同校验和内部审批 |
| 市场资料 | 欧盟官方纺织品标签资料及人工整理条目 | 展示外部来源到业务规则的过程 |

**初始输入：**「德国买家询问 3,000 件 SKU A 成人 T 恤，常规包装。先做英文 RFQ 回复和英文报价草稿，内部摘要用中文。报价贸易条件、付款与有效期采用我确认过的商家模板。」

系统生成 V1，并指出买家原文若要求“100% cotton”，则与 SKU A 规格冲突；可以改用准确成分，或请业务员确认是否选择 SKU B。未解决的关键规格冲突不进入最终审核。

**第一轮迭代：**「买家改成 1,500 件，加礼盒，20 天交货，并需要德文版。」

生成 V2 待确认稿：重新选择数量档位；礼盒费与加急交期标为待确认；显示变化和采购任务；德文文案不能写成已承诺 20 天。

**第二轮迭代：**「保持 SKU A 的真实成分，恢复常规包装，按已确认的 30 天交期；使用现有 1,500 件档位价格，更新德文报价和中文采购确认单。」

生成 V3：计算已知费用、删除未采用的礼盒与加急承诺、更新全文和 PDF，展示 V1→V3 的数量、单价、总额、描述与交期差异。通过适用检查后进入审核。

备用演示可以选择 SKU B，但要完整重算，不能只把商品名称替换。现场两次操作应实际产生新版本和调用记录，不通过预先写死文本模拟模型运行。

# 7 本地化与规则校验

## 7.1 两个场景和两种语言

| 场景 | 英语产出 | 德语产出 | 业务适配 |
| - | - | - | - |
| RFQ 首轮回复 | 产品匹配、核心条件、关键澄清问题 | 按同样事实生成礼貌、清晰的商务回复 | 短文本先回答买家问题，区分已知与待确认 |
| 邮件正式报价 | 正文、条款摘要、附件说明 | 德语邮件及报价 PDF | 使用明确型号、计量单位、币种、日期、有效期与责任范围 |
| 内部协同 | 不必额外翻译 | 不必额外翻译 | 中文说明变更、成本与待办，保留买家原文引用 |

本地化模板需独立处理称呼、术语、数值格式和行动请求。德文报价可按目标读者习惯显示小数、千位和日期；数据库保存统一数值，不从格式化字符串反算金额。不能根据国籍猜测个人偏好，客户已确认的表达习惯优先。

把术语表、禁用夸大表述、标准条款和版式模板分别版本化。生成后检查两种语言的 SKU、材料、数量、币种、金额、日期和贸易条件是否一致。RFQ 适配引用组织者提供的最新平台文档；未导入正式规则时，不声称已经覆盖全部阿里国际站规则。

## 7.2 至少两类校验

第一类为**合同与交易条款**：报价有效期、币种、计量单位、数量与总额、付款比例合计、交期起算条件、指定交货地点，以及使用 Incoterms 时的规则和版本。贸易术语不自动补全付款时间和全部合同安排。[11]

第二类为**选定目标国规则**：对本次成人纺织品演示，核对商品材料证据与标签文案，检查是否错误使用“100%／pure／all”等单一纤维表述；核对目标销售市场适用的语言要求。欧盟官方资料同时区分面向消费者的标签与 B2B 商业文件情形，因此规则必须先判断业务适用范围。[10]

| 检查项示例 | 证据 | 反馈动作 |
| - | - | - |
| 规格为 95% 棉＋5% 氨纶，文案却写 100% 棉 | 商品规格版本＋对应规则来源 | 阻断错误文案，建议准确描述 |
| 付款比例合计不为 100% | 结构化条款 | 阻断，并定位到问题字段 |
| 20 天交货尚无供货确认 | 供应商确认记录 | 待内部确认，禁止改写为确定承诺 |
| 使用贸易术语但缺少指定地点或版本 | 报价字段与商家模板 | 要求补齐，不由模型随意填入 |
| 规则无法确定是否适用于该产品／交易 | 适用条件或资料不足 | 待核实，列明需要的证据 |

反馈至少实现：①字段旁红／黄／灰风险标记；②文本批注解释原因、来源和建议；③版本差异对比。颜色之外保留文字状态，避免仅凭颜色理解。

目标国检查仅覆盖已明确建模的条款。输出使用「本次已检查项目」和「未覆盖／待核实项目」，不把少数规则通过表达成全面法律合规认证。

# 8 技术架构与复用边界

**推荐实施路线：Fork Solivio，保留其 React／Next.js 业务界面与数据库，以新增适配层接入 DeepSeek Harness。** 时间主要投入业务闭环，不为比赛重写已有界面。

Solivio 当前采用构建时组合的模块化单体，模块不是可直接安装到 Harness 的独立插件。其现有 Agent 实现使用 VoltAgent；替换为 Harness 涉及实际适配工作，不是改一个模型名称。[4][5][6]

| 层 | 选型／职责 | 本队工作 |
| - | - | - |
| 业务界面 | Solivio 的目录、报价、聊天、知识与 PDF 页面 | 汉化、岗位任务、风险与差异面板、目标语言模板 |
| 业务服务 | Solivio 模块服务及新增扩展 | 权限、状态、版本、价格计算、规则校验 |
| Agent 执行 | DeepSeek Harness 的 SDK／插件机制 | 构建限定业务工具的 profile，接入业务服务 |
| 模型 | 单独配置的模型提供方 | 验证工具调用、结构化输出、流式返回与实际模型可用性 |
| 业务存储 | PostgreSQL，按需要使用 pgvector | 保存商品、价格、报价快照、审批和检索索引 |
| 知识源 | 原始资料＋版本化 Markdown Wiki | 来源登记、草稿、人工发布、索引同步 |
| 文档产出 | 复用 offer-pdf 并改模板 | 德文字体、长文本换页、金额与版本一致性 |
| 后台任务 | 沿用现有任务基础设施 | 文档处理、索引更新、受影响单据任务 |

Harness 支持 SDK 和插件扩展，本方案通过业务工具插件扩展运行能力。[8] 部署时可由应用服务管理 Harness SDK 进程；新增窄接口桥接层调用 Solivio 服务。这个桥接层是本项目要实现的内容，不能把 Solivio 当作已经提供完整公开业务 API 的服务。

拟定运行链路：

1. 页面提交用户消息、当前单据 ID 和版本。

2. 服务验证登录与单据权限，创建 runId 和快照。

3. Harness 获得当前任务、允许的业务工具及必要上下文。

4. 工具经适配层读取商品、知识和报价，或请求有权限的草稿变更。

5. 业务服务完成计算与校验，返回结构化结果和来源。

6. Agent 生成解释与本地化内容；服务再次检查结构一致性。

7. 页面展示结果、证据、风险、版本差异与待办。

MVP 用一个受控执行会话完成任务，业务员、采购、审核人是产品角色，不要求各创建一个自主 Agent。需要时可拆分生成与校验调用，但核心金额和审批状态必须由业务代码决定。

## 8.1 逐模块复用

| 上游模块／能力 | 复用内容 | 需要补齐 |
| - | - | - |
| catalog、csv-import | 商品目录、导入基础 | 外贸字段映射、单位币种、成本与数量档位 |
| customers、order-history | 客户与历史成交参考 | 授权数据范围、历史价格有效性提示 |

# 9 业务工具与数据模型

以下为本项目拟定义的业务工具，并非宣称上游已提供同名 API。

| 工具 | 主要输入 | 返回内容 | 权限 |
| - | - | - | - |
| parse_inquiry | 原文、语言、场景 | 需求字段、原文位置、缺项 | 读 |
| search_catalog | 产品条件、数量、市场 | 候选 SKU、匹配差异、数据版本 | 读 |
| search_knowledge | 问题、市场、产品范围 | 条目、来源片段、版本、状态 | 读 |
| calculate_quote | 商品、数量、成本快照、币种参数 | 明细、总额、内部毛利、缺失项 | 无副作用计算 |
| validate_quote | 报价快照、适用规则版本 | 检查结果、理由、依据、修订建议 | 无副作用检查 |
| create_quote_revision | 单据、expectedRevision、变更、幂等键 | 新版本、差异、受影响字段 | 授权写入草稿 |
| create_review_tasks | 未决事项、责任岗位、单据版本 | 可跟踪任务 | 授权内部写入 |
| render_quote_pdf | 已保存的单据版本、模板、语言 | PDF 引用与版本 | 受控导出 |

知识发布与最终审批通过明确的人员操作完成，不作为普通销售聊天工具默认授权。运行时的通用 Shell、任意文件写入和无限制网络访问不属于业务所需工具集。

所有工具返回统一结构：状态、data、evidence、warnings、revision、errorCode；工具失败不能伪装成“检索无结果”。服务端从认证上下文确定用户权限，不能信任模型自报的角色。

建议新增或扩展的数据对象：

- Inquiry：原文、来源、语言、客户、提取字段、缺失字段。

- Product／PriceRevision：规格、单位、币种、数量档位、有效期、来源。

- Quote／QuoteRevision／QuoteLine：单据身份、每版快照、明细与商业条款。

- RuleCheck：ruleId、规则版本、适用条件、结果、依据和人工处理。

- SourceDocument／WikiRevision／Citation：来源、知识版本、事实引用。

- ReviewTask／Approval：待办、责任人、所依赖版本与审核结果。

- AgentRun／ToolCall：运行标识、工具参数摘要、结果、耗时和失败状态。

报价快照固定商品版本、价格版本、规则版本、知识引用和模板版本。现有表能表达的字段优先扩展；新模块遵守 Solivio 的服务边界，不直接跨模块修改私有表。知识引用必须能反查受影响单据。

金额使用十进制定点计算。需明确：

- 行金额＝数量×单价，折扣与附加费用按已定义顺序计算。

- 采用人民币成本、美元报价时，明确汇率变量表示「人民币／美元」，成本美元值＝成本人民币值÷该汇率。

- 内部毛利率＝（收入－纳入本次计算的成本）÷收入；不能与成本加价率混用。

- 未计入税费、运费或其他成本时必须列明；汇率来源、时间和采用值随报价冻结。

- 舍入规则统一，校验行金额之和与总额一致；币种不同的金额不能直接相加。

AI 可以解释计算结果，不能自己重新编造另一组数字。

# 10 用 LLM Wiki 组织企业知识

Karpathy 的原始资料描述的是以原始来源、互相链接的 Markdown 知识页和 LLM 维护流程组成的思路，而不是已经安装即可用于企业报价的完整产品。[12] 本项目自行实现下面的业务版本。

## 10.1 三类信息分开管理

| 信息 | 权威存储 | 原因 |
| - | - | - |
| SKU、成本、库存、报价、审核状态 | 业务数据库 | 要求结构化约束、及时更新与准确计算 |
| 企业经验、流程、术语、市场资料解读 | 版本化 Wiki | 便于组织知识、引用来源与人工修订 |
| 供应商文件、官方文档、授权原件 | 原始资料存储 | 需要回溯证据、核对上下文与版本 |

Wiki 不替代数据库，也不排斥 RAG。Wiki 负责知识维护，Solivio 的文章与检索索引承载查询副本；引用始终回到已发布 Wiki 版本及原始来源。小规模可先用关键词＋结构导航，已有向量检索经验证可继续使用，不必为了演示引入额外图数据库。

建议目录为 raw、wiki/products、wiki/processes、wiki/markets、wiki/terms、wiki/customers，以及 index.md、log.md 和 schema.md。客户专属知识与通用市场知识分开授权；写入任务按知识空间串行处理，避免并发覆盖。

## 10.2 知识生命周期

1. 登记来源：文件哈希、来源 URL 或上传人、授权说明、采集时间、版本。

2. 抽取候选知识：保留页码／段落位置，区分原文事实与模型推断。

3. 检查：来源缺失、断链、相互矛盾、适用市场和有效期。

4. 人工复核：业务知识维护人确认，可拒绝或改写。

5. 发布版本：记录发布人、差异和引用，更新检索副本。

6. 影响分析：找出引用旧条目的未完成报价，创建复核任务。

7. 定期维护：到期提醒、失效标记和冲突队列。

每个已发布条目至少保存 sourceIds、sourceLocations、applicableMarkets、productScope、validFrom、validTo、checkedAt、status、reviewer、version。市场规则还要保存适用条件，不能只凭关键词命中就套用。

遇到冲突先比较来源权威性、适用对象和生效条件，再比较时间；新上传的销售笔记不会自动推翻供应商正式规格或适用法规。模型生成的报价与回答可以进入复盘候选区，不能直接成为新的事实证据。

## 10.3 黑客松最小知识集

目标准备约 15～25 份有权使用的资料，整理为约 20～40 个小条目：产品规格、供货限制、报价 SOP、付款与交期模板、英德术语、选定目标市场规则。数量是建设目标，不代表已经收集完成。

优先保证每个条目真实有用：谁会问、在哪一步调用、影响哪个字段、来源是什么。验收时至少展示一次真实检索、一次来源打开、一次冲突阻断；知识更新触发报价复核作为时间允许时的加分演示。

# 11 稳定性与异常处理

| 异常 | 处理方式 | 用户看到的状态 |
| - | - | - |
| CSV 列缺失、单位未知 | 返回逐行错误，保留原文件和映射 | 哪一列需要修正，可重新导入 |
| 商品没有准确匹配 | 返回候选差异并追问 | 未匹配／待确认，不偷换材料或品牌 |
| 价格、包装费、交期缺证据 | 允许保存未定草稿，限制最终审核 | 明确缺项与负责岗位 |
| 模型超时或限流 | 有界重试；持久化已完成步骤 | 本次未完成，可从保存点继续 |
| 工具部分失败 | 保存成功结果，失败步骤单独重跑 | 展示失败的数据源及影响 |
| 知识来源过期或矛盾 | 排除不适用版本或进入复核 | 来源冲突，不能显示为检查通过 |
| 并发修改或重复提交 | expectedRevision＋幂等键 | 已更新，请对比版本后重试 |
| PDF 生成失败 | 保留结构化报价，允许再次渲染 | 报价已保存，附件待生成 |

每次运行记录 runId、单据版本、工具调用、数据来源版本、模型配置、耗时和错误。敏感输入在日志中按需脱敏；原文只在必要范围传给模型。外部询盘和文件内容作为数据处理，不能借其中的文字扩大工具权限。

现场准备健康检查、固定数据集、数据库备份／重置脚本、PDF 字体预装和失败恢复按钮。对模型、数据库、索引和文件服务分别展示连接状态。缓存用于已知资料与固定模板；如果使用录屏或回放作为断网备用，应明确标记，不冒充实时调用。

初始运行限制可以设为每次任务最多 8～12 次工具调用、明确的超时和费用上限，之后用实测调整。这是拟定配置，不是上游默认值，也不是对现场响应时间的保证。

# 12 开发排期与人员安排

以下按 2 名开发＋1 名兼职外贸业务验证者、7～10 个工作日估算；前提是上游工程能正常启动、模型额度可用、商家数据及时到位。它是项目计划，不是已验证的工时承诺。

| 阶段 | 工作 | 阶段验收 |
| - | - | - |
| 第 1 天 | 固定上游版本、启动 Solivio、跑通 Harness 最小工具与结构化输出、完成许可清单初稿 | 可以读到真实演示商品并返回引用；发现集成阻碍即调整路线 |
| 第 2～3 天 | 数据字段、CSV 导入、询盘结构、确定性计算、V1 草稿 | 目录→询盘→报价链路可运行，金额有依据 |
| 第 4～5 天 | 英德模板、目标国与合同规则、风险批注、PDF | 两场景输出可读，已知冲突能拦截 |
| 第 6～7 天 | 修订依赖、版本对比、岗位任务、知识来源映射 | 两轮变更后各产出与当前事实一致 |
| 第 8 天 | 补异常恢复、关键权限、评估集与连续演练 | 不覆盖旧报价，工具失败可见 |
| 第 9～10 天 | 修复关键问题、冻结版本、交付包、海报与路演 | 全套验收、离线备用材料和 hackathon-final 标签 |

开发 A 负责业务界面、报价编辑、PDF 和演示；开发 B 负责 Harness 适配、业务工具、数据、规则与知识链路。业务验证者负责样本、术语、规则适用范围和报价复核，不由工程团队凭空编造外贸事实。

如果只有 48～72 小时，保留：单商家、单品类、手动询盘、CSV 商品、预先审核好的 Wiki、两个工作流、英德输出、两类检查与两轮修订。删掉：自动 Wiki 编译、批量队列、真实邮箱接入、复杂买家背调、多租户、自动外发。即使缩减，也不能把赛事基础验收项删掉。

技术集成优先用半天以内的验证暴露风险；若底层 Harness 适配在可用时间内无法完成，用实际可运行的执行层交付业务闭环，并如实调整架构说明。

# 13 验证方法与业务指标

先准备 10 个开发样例用于调整；另设 20 个保留样例验证，避免只对现场样本优化。30 个样例的建议分布：

| 类型 | 数量 | 检查重点 |
| - | -: | - |
| 信息完整与缺项询盘 | 6 | 提取、单位、缺项追问 |
| 数量档位、费用和币种 | 6 | 计算、舍入、成本缺失 |
| 材质与市场规则冲突 | 4 | 适用范围、来源和错误文案 |
| 合同条款缺失与矛盾 | 4 | 付款、交期、有效期与地点 |
| 两轮变更与多语言一致性 | 4 | 全部受影响字段是否更新 |
| 超时、重复提交、并发与来源失效 | 6 | 恢复、版本与失败提示 |

确定性逻辑用自动化检查：金额、状态转换、幂等、版本冲突和权限。语言与知识回答用人工标准评分：事实一致、来源支持、术语准确、表达适合场景、下一步可执行；不要求逐字匹配预期句子。

拟定发布门槛：

- 在评估集内，金额与确定性规则计算无错误；所有已知必填缺口可见。

- 在评估集内，价格、材料、交期等事实承诺有数据或明确待确认标记。

- 不覆盖已发送版本，不让无权限用户完成审批。

- 两轮修订后，页面、正文与 PDF 的关键字段一致。

- 重置后连续完成 5 次主流程演练；任一失败均定位并修复后再计数。

以上是待验证目标，不能在海报上提前写成已达成结果。

业务试点用同一批匿名询盘比较人工方式与辅助方式，记录：

1. 首份可审核报价用时的中位数。

2. 每单澄清往返次数。

3. 人工需要纠正的事实或金额错误数。

4. 需求变更后漏更新的字段数。

5. 岗位任务从提出到确认的时间。

6. 每个完成单据的模型与基础设施成本。

询盘转化率可作为长期跟踪指标，黑客松期间不根据少数演示推导实际成交增长。

# 14 成本与商业化假设

成本按实际完成业务单据计算，而不是只算一次聊天：

- 单据模型成本＝各模型调用的输入费用＋输出费用＋必要的重试费用。

- 单据总服务成本＝模型＋检索／存储／文档渲染＋外部数据成本。

- 商家可验证收益＝节省的处理时间×人工成本＋减少返工的价值。

模型价格、额度与第三方数据套餐在选定实际供应商后按当期官方价格填入预算；本方案不以未核验的实时单价计算商业利润。先运行 20 单测量平均值和高耗时样本，再设置单次与每日上限。

首批获客建议找 3～5 家有现成商品表与英文询盘的商家做访谈，其中至少 1 家提供脱敏测试数据；询问最近一次改报价出错的具体过程，而不仅问“你愿不愿意用 AI”。

收费可试验「一次性数据整理／部署＋按月服务」，报价依据用户数、单量和维护工作量确定；收费意愿必须通过试点验证。早期可采用每商家独立实例交付，符合当前复用基础，等有真实需求再建设共享多租户架构。

潜在壁垒来自长期积累的行业字段、经过验证的规则、真实变更案例和商家知识维护流程。MIT 代码复用能缩短起步时间，本身不构成商业壁垒。

# 15 三分钟路演与现场演示

| 时间 | 展示 | 要说清的价值 |
| - | - | - |
| 0:00～0:20 | 一张真实业务流程图或匿名案例 | 一次买家改需求，会牵动价格、交期、条款与采购 |
| 0:20～0:40 | 商品目录、知识来源和演示商家 | 报价依据来自哪些数据 |
| 0:40～1:15 | 工作流一：输入询盘，显示检索与 V1 | 从原文到可审核草稿，并指出材料冲突 |
| 1:15～1:50 | 第一轮：改数量、礼盒、交期和语言 | V2 差异、缺成本、未确认交期及采购任务 |
| 1:50～2:20 | 第二轮：确认真实材料、常规包装和 30 天 | V3 重算、风险处理、德文输出 |
| 2:20～2:40 | PDF、中文内部任务、来源定位 | 同一事实同时服务买家、业务和采购 |
| 2:40～3:00 | 架构与验证结果 | 复用了什么、新增了什么、已实测什么 |

每个模型步骤只生成演示所需的短内容，减少等待；录屏用于备用，不替代现场真实调用。现场模型较慢时，把执行状态和已完成工具结果展示出来；不要伪造实时完成。

建议路演材料 5 页：业务问题；两个工作流；数据与知识架构；现场效果与验证；开源复用及下一步。标题可用「买家一句改需求，报价、风险和采购一起更新」，避免用未经测试的效率百分比。

**0.8×1.8 米海报建议结构：** 上部约 25% 放一句定位和目标用户；中部约 45% 放两个工作流与前后差异截图；下部约 20% 放数据来源、技术方案和实际验证结果；底部约 10% 放演示二维码、团队与开源致谢。印刷时按印厂要求准备出血、字体和图片分辨率。

# 17 实施前的具体准备

第一批输入材料只需要：一份有权限使用的商品表、5～10 份脱敏询盘、2～3 份历史报价、已确认的商业条款、少量供应商规格与交期说明。拿不到真实资料时可以先用明确标识的合成数据验证工程，但路演应诚实说明真实商家验证尚未完成。

启动顺序：

1. 固定 Solivio 与 DeepSeek Harness 的具体提交，保存许可和版本记录。

2. 验证启动、登录、商品导入、现有报价与 PDF，确认实际运行基线。

3. 打通一个 Harness 业务工具，验证工具参数、权限、返回值与流式事件。

4. 冻结一个品类的数据字段、两个业务场景和演示样本。

5. 先交付“询盘→报价→两轮变更→复核→PDF”的纵向闭环，再扩展批处理和知识自动维护。

建议把立项说明写成：\
“我们基于 MIT 开源组件构建外贸询报价协同应用，新增有来源约束的企业知识、外贸条款校验与需求变更传播机制。买家修改需求后，系统同步生成报价差异、目标语言回复及内部确认任务，帮助业务员和采购围绕同一份事实协作。”

目前已经核验的是上游许可、相关模块文档与关键源码；上述功能和性能需要在实施后逐项验收。
