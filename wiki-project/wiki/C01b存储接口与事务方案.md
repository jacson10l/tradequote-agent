# C01b 存储接口与事务方案

本文是可交接的设计草案，不是已经实现的存储服务。准备分支codex/c01b-storage-plan从共同基线45a9975506030170bcb8dc770919b7cb5de89fa6建立；没有把未合入的B00/C01a源码复制进来。固定参考B00的4e8c663（[PR #1](https://github.com/jacson10l/tradequote-agent/pull/1)）、C01a的68455a3（[PR #2](https://github.com/jacson10l/tradequote-agent/pull/2)）和复核提交2db64b4。准备时读取远端，两PR均OPEN；后续B00/C01a已完成独立技术复核并纳入本次收口候选，实际交付见 [[分支收口与共同基线]]。A迁移4仍未进入共同基线。

## 当前实现与切片目标

现有SqliteWorkspaceRepository拥有唯一业务连接，WAL、foreign_keys、synchronous=FULL已设置。TradeStore.commitAgent在同步IMMEDIATE事务内写报价、agent_turn、outbox、成功idempotency；模型等待在事务外。现有idempotency.result_json是TradeResult，不能写入queued/RunResult。C01a另分支已有状态转换和进程内cancel；它没有run表、恢复服务或正式运行IPC。

C01b目标为单工作区、单写worker的持久化run服务，保持旧报价字节和旧understand/revise返回值。C01c再启用桌面start/get/cancel/retry和UI；本次不启用这些入口，不新增数据库或伪造成功mock。完整业务知识整理依赖另项B00a，不阻塞报价run。

## 内部存储接口草案

以下签名是设计记法，仅在业务worker内调用，不是新公共DTO或已编译代码。AgentRun/RunCommand/RunResult复用B合入后的公共类型；Understanding/RevisionProposal/ExecutionContext沿用现有公共导出。UUID和时间由宿主生成/注入，workspace由已绑定repository决定；模型和renderer不能提供执行票据。

| 方法 | 输入 → 输出 | 保证 |
|---|---|---|
| start | Extract<RunCommand,{method:"agent.start"}>、ExecutionContext → RunResult＋dispatch:null或{runId,attempt} | 事务内校验、入queued、记outbox；仅首次创建返回dispatch，事务失败不派发 |
| get / list | runId / B确定的有界查询 → RunResult / RunListResult | 只读当前工作区；不存在NOT_FOUND；按不可变createdAt/runId作keyset分页，get查当前状态 |
| claim | runId、expectedAttempt、workerSessionId → claimed{ticket,command}或skipped{run} | CAS queued到running，生成executionId；重复调度不重复领用，不在此调用模型 |
| finishWithoutQuote | ticket、{kind:waiting_input,clarification}或{kind:failed,error} → RunResult | 只接受当前running尝试，写有界解释＋outbox；不写报价成功幂等 |
| commitQuote | ticket、Understanding或RevisionProposal、modelId → RunResult | 同一事务完成报价、对话、报价幂等、outbox、run引用；不暴露任意回调/原始DB给调用方 |
| cancel | Extract<RunCommand,{method:"agent.cancel"}>、ExecutionContext → RunResult＋abort:null或ticket | 先持久化终态和控制幂等，再中止对应尝试；已completed返回原提交事实 |
| retry | Extract<RunCommand,{method:"agent.retry"}>、ExecutionContext → RunResult＋dispatch:null或{runId,attempt} | 新控制动作且状态允许才递增attempt并入queued；保留原command和operationKey |
| recoverOnStartup | 新workerSessionId（宿主注入） → affected runIds | 确认旧worker已退出后，将旧queued/running原子标interrupted；不自动派发或调用模型 |

ticket是内部执行栅栏：{runId,attempt,executionId,workerSessionId}。所有异步返回在事务内再次匹配ticket与running状态；旧尝试、旧worker、取消后晚到结果只回读当前快照，不改当前run。控制副作用由事务结果携带，重放副作用为空。取消的AbortController索引须绑定executionId，不能沿用operationKey单独索引去中止刚启动的新attempt。cancel落库失败不得报告取消成功或先abort；落库成功但abort未执行即崩溃也不能提交已取消run。

cancel只转换queued/running/waiting_input；cancelled重复取消保持原态，不重复状态事件；completed返回完成事实；failed/interrupted拒绝取消，保留原因。list不是跨页状态快照，过滤按每页读取时的状态执行，运行状态变化后须刷新第一页；不可承诺动态过滤时永不遗漏。恢复发现默认不按状态过滤，按稳定顺序读全部，再get确认需要操作的run；新增run在下一轮刷新发现。B需在游标契约和R18中明确此行为。

## 表与幂等设计（待A确认）

| 数据 | 建议存储与约束 |
|---|---|
| agent_run | run_id主键；workspace_id外键；operation_key在工作区唯一；command_json和request_hash不可变；status/attempt、created_at/updated_at；base_revision_id、committed_revision_id；clarification、公开error_json；worker_session_id、execution_id（内部字段不出IPC） |
| agent_run_control | UNIQUE(workspace_id,control_key)，method、run_id、request_hash、首次result_json；与控制转换同事务；同key异参冲突。与旧报价idempotency隔离 |
| outbox | 复用现有表记录开始、领用、取消、中断、澄清、失败、完成；不新增第二份事件库。仅在真实转换时追加，有界脱敏payload；本切片不声称流式RunEvent.seq协议已经实现 |
| idempotency | 现有成功TradeResult保持原格式/原agentHash算法；start不会提前占用该键，成功后仍由报价提交写入；同键冲突统一检测 |

attempt表示已获准的逻辑尝试：初次queued为1，每次新retry事务加1，claim/replay/get/recover不加；它不等于实际HTTP计费次数。status用既有枚举，attempt>0；completed当且仅当committed_revision_id非空，非waiting_input的clarification必须null。base引用与command一致。V1和修订分两表，committed_revision_id不能只外键引用quote_revision；由同事务显式核验V1/修订身份、workspace、command/turn关联，不从board.quotes[0]猜测版本。现有通用job表保留原用途，不双写成另一套run真相。

start检查既有报价成功幂等：不同参数返回冲突；相同命令且成功已提交，可建completed运行投影并返回dispatch=null。必须从经过schema验证的持久化结果、对应agent_turn与报价快照核实准确版本，缺失/不一致返回STORAGE_ERROR且不重调模型；不能把任意evidenceIds首项当可信结果。新完成路径明确返回committedRevisionId。旧业务接口与新run共用key时，仍须在统一执行协调器中避免双重派发；C01c开放新IPC前补R17。

## 事务和崩溃边界

1. start：BEGIN IMMEDIATE → 校验workspace/业务指纹和已存run/旧成功记录 → 插入queued或已完成投影＋outbox → COMMIT → 才安排claim。重复start不唤醒interrupted。
2. claim：BEGIN IMMEDIATE → CAS queued和expectedAttempt → running＋executionId/session＋outbox → COMMIT → 在事务外读取受控模型配置、调用模型。凭据只在内存，不写表/事件。
3. 完成：BEGIN IMMEDIATE → 检查ticket/status、原业务幂等、最新报价基线 → 确定性计算 → 插入quote/turn＋报价outbox/idempotency → 更新run completed/committedRevisionId并清理执行票据＋run outbox → COMMIT。任一步异常回滚整个事务；不能先commitAgent成功再另开事务更新run。
4. 取消：BEGIN IMMEDIATE → 查控制幂等、run终态 → 允许时持久化cancelled并使ticket失效、清clarification＋outbox → 存首次控制结果 → COMMIT → abort旧ticket。完成先提交则返回completed且不abort；取消先提交则后续模型回调不能落报价。
5. retry：同事务检查控制幂等和许可状态；同key重放不增attempt、不调模型。新retry保留原命令，生成下一次queued；派发丢失由重启interrupted暴露，不能后台自动重发。
6. 重启：宿主取得独占写入权并确认旧worker退出，再恢复旧queued/running为interrupted、使旧ticket失效；保留attempt/command、记公开中断原因/outbox。completed/failed/cancelled/waiting_input不改。恢复事务失败则不启动调度；重复恢复不重复事件。get/list不触发收费请求。

同步事务内不await网络。C提出TradeStore内部重构：抽出同连接的提交核心，显式返回{tradeResult,committedRevisionId}，旧commitAgent仍由原包装方法执行事务并返回TradeResult；新run提交由外层唯一事务调用该核心。核心/原始DB不作为renderer、Agent或跨包公开能力。A复核连接与导出；B复核报价/幂等兼容性。业务失败处理也先确认事务已回滚，再以独立短事务写当前ticket的failed；若失败落库再次出错，保持可恢复状态并报告存储错误，不假写failed/completed。后续重新打开的queued/running由恢复流程处理。

成功报价持久化可以做到一次；外部模型请求无法保证崩溃后的恰好一次计费。模型已收费但本地未提交时，重开只提示interrupted，由用户显式决定是否再次调用。不得把恢复设计宣传为所有重试均免费。
