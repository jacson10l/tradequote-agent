# 0005-M1工程初始化边界

## 背景

M0 已验证本机 Electron/SQLite 路线，用户要求开始 M1。三人契约评审和最终安装尚未完成，需要可运行工程同时保留真实进度边界。

## 决定

正式 pnpm workspace 与历史 experiments 隔离。先交付工作区纵向切片，使用窄 IPC、Utility Process 单写入、strict DTO 与 ports；初期 workspace 服务放 domain，后续用例增多再提取 application。UI 接入既定 React/Tailwind/shadcn 组织方式及表单/查询/路由，不用 M0 HTML 冒充正式工程。初始化任务 active，后续 M1 范围继续跟踪。

依赖采用实际 registry 元数据与本机安装结果锁定；保留 Node 22.22.0 与 Electron 44.9.2。原生单元测试运行在 Electron Node ABI，避免与产品二进制冲突。jsdom 26.1.0 满足当前 Node 组合。默认最小 Agent 执行器不变，本轮不引入 Harness 生产依赖。

## 替代方案

把所有未来包预建为空壳不能验证真实边界；把完整报价/Agent 同时塞进初始化会超越 T00 未评审契约；让测试每次重建 Node/Electron 两种 SQLite ABI 会增加本地与 CI 不一致。故使用真实工作区持久化与 Electron 单一 ABI 作为基础。

## 后果

已能用真实桌面和数据库开发协作接口，但并不具有正式报价/模型能力。Job/outbox 先有基础表，消费和恢复后续实现。Windows 与安装发布仍需真实验收，不能根据本机 E2E 推断通过。

## 回滚方式

M0 与规则基线 commit 保留，可切回独立探针。M1 schema 拒绝高版本降级；撤回应用代码时先备份工作区，不能删除数据库或盲目降低 user_version。依赖升级另立验证记录并保持锁文件与 Wiki 同步。
