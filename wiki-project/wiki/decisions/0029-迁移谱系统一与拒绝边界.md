# 0029 迁移谱系统一与拒绝边界

## 背景

三方迁移存在编号冲突：C 的 5/6/7 是 run 表（agent_run/agent_run_control、agent_write_call、agent_tool_step+validation_json），A 的 6 是知识四表，B 的 7 是 quote_check_report。相同 user_version 不代表相同 schema。六组证据（`c-b01-migration-compatibility-probe.json`）暴露四类缺陷：D1 C7→B7 被当 UNKNOWN_LEGACY 拒绝；D2 B7→C7 无操作却静默缺 run 表；D3 C6→B7 按 v6 误记 A/B 知识指纹却无知识表，产生矛盾账本；D4 C5→B7 拒绝。B 的两项负向诊断还发现「未知 v6 被误接受」与「缺不可变触发器仍被接受」。迁移顺序由 A 维护，本决定确立 A 的统一谱系与拒绝边界，作为 B 接口/报告适配与 C 独立组合验证的固定依据。

## 决定

1. 识别只以实际 schema（表/索引/触发器/列/外键/CHECK 及其有效定义）为准，user_version 仅作交叉核对，绝不单独依据编号判定谱系。新增 `migration-lineage.ts` 纯函数把 schema 归入九个能力切片（common 1~4、c-run 5/6/7、knowledge-wiki 6、check-report 7），再按精确的 present 集合分类谱系。
2. 每个能力切片用 `(lineage, version)` 作身份，账本 `migration_registry(lineage,version,sql_hash,applied_at)` 以 (lineage,version) 为主键，区分 C6 与 A6、C7 与 B7；旧 B 的 `schema_migration` 表不删不改，只做 hash 交叉核对。
3. 统一目标为九个能力齐备、user_version=8；历史 SQL、账本、业务事实一律不改写，缺失能力按 MIGRATION_STEPS 顺序定向追加，已存在能力核对指纹后补记账本。
4. 拒绝位置前置到只读预检：打开文件前先只读识别，拒绝即抛 `MIGRATION_LINEAGE_REJECTED:<lineage>`，不进入读写真开、不写 -wal/-shm、不改 user_version、不建账本。逐谱系支持/拒绝见 [[A01-迁移谱系支持与拒绝矩阵]]，追加设计与执行身份见 [[A01-追加迁移设计]]。

## 替代方案

- 继续按 user_version 单号判定：无法同时表达 C6 与 A6、C7 与 B7，必然复现 D2/D3 与未知 v6 误接受，放弃。
- 三方重排编号统一线性序列：会改写已发布迁移的版本语义，破坏历史 SQL/账本/业务事实，且需要 C/B 同步改各自已冻结实现，放弃。
- 拒绝时只做一次读写真开后回滚：会在磁盘留下 -wal/-shm 与打开痕迹，且回滚前有竞争窗口，不符合「拒绝不修改 DB」，放弃，改为只读预检。
- 用能力存在与否但不核对触发器：会复现「缺不可变触发器仍被接受」，放弃，改为对象级 partial 判定。

## 后果

- A 新增 `migration-lineage.ts`、重写 `migrations.ts`，`index.ts` 构造器前接只读预检；三个旧迁移测试改走 `seedTo`/`migrate`，断言 user_version=8。
- B 需按谱系账本适配接口/报告/消费，并提供事务证据；C 需在独立组合 worktree 验证全矩阵后接桌面跑 macOS 全量验证。三者非 A 单方面完成。
- 旧库保留原样，任何矛盾（混合谱系、缺触发器/索引/列、账本 hash 不符、user_version 不符）都安全拒绝而非静默放行。

## 回滚方式

本决定是迁移识别与追加逻辑的收敛，不删除任何历史表或改写旧账本；回滚为回到本决定前的 `migrate` 实现即可，已有数据库不受影响。已按统一目标升级的库不能靠删表回退，需保留账本与历史审计。

## 二轮核验修正（M13 与 A-W08，2026-10-24）

C 二轮独立复核（20891fb）确认首轮 N07～N11 与类型门禁已关闭，但指出 `capabilityStatus` 的索引/触发器只做关键词存在性检查，不足以证明约束「有效」：M13-X01 触发器 `WHEN 0` 永假、M13-X02 部分索引 `WHERE 0` 不索引任何行、M13-X03 删除外键、M13-X04 删除 CHECK，均被误识别为 c-v7/c-v6 并升级。A 补足有效定义判据：

- 触发器/索引谓词：`extractPredicate` + `isConstantFalse` 判定 WHEN/WHERE 是否为字面 `0`/`false`/`null` 永假，永假即 partial/tampered（M13-X01/X02）。
- 外键：`CapabilitySpec.foreignKeys` 记录子表列→父表列，`snapshotSchema` 用 `PRAGMA foreign_key_list` 收集实际外键，缺失即 partial/tampered（M13-X03）。
- CHECK：`CapabilitySpec.checks` 记录表 + 谓词正则，按 sqlite_master 表原文匹配（SQLite 无 CHECK 专用 PRAGMA），缺失即 partial/tampered（M13-X04）。

A-W08 独立修正：`CAPABILITY_UNAVAILABLE` 的 `retryable` 统一为 `false`（能力未接入是确定状态而非瞬时故障），修正 `contracts` `failure()` 中 `retryable: code === "CAPABILITY_UNAVAILABLE"` 的特例，属公共契约单行修正待 B 评审确认，见 [[A对C前置验证失败修正回复]]。

探针扩至 23 用例（新增 M13-X01～X04 四个负例）全过；`wiki-store.test.ts` A-W08 转绿，整仓 infrastructure vitest 44 通过/1 既有失败（Windows symlink EPERM）。

## 三轮核验修正（M13 有效定义变体 X05～X09，2026-10-24）

C 三轮独立复核（a633c42，`codex/c-a-lineage-third-validation`）确认原 M13-X01～X04 通过、A-W08 已关闭，但指出关键词/少数常量黑名单仍不完整：`1=0` 等价永假未被拒（X05/X06）、索引目标列与谓词未核对（X07）、触发器事件未核对（X08）、CHECK 正则命中注释（X09）。C 建议复用规范参考 schema/可审阅结构判据。A 放弃常量黑名单，改为结构核对：

- 触发器：`TriggerRequirement` 增加规范 `event`（DELETE/UPDATE/INSERT）与 `when`（`null`=必须无 WHEN，字符串=归一后精确匹配）；事件不符（X08）或加/改 WHEN（X05）即 partial/tampered。
- 索引：`IndexRequirement` 增加规范 `columns` 与 `where`，索引列与 WHERE 谓词归一后精确匹配（X06/X07）。
- CHECK：`stripComments` 去注释后再按表原文匹配（X09）；`quote_check_report_revision` 的复杂 WHEN 不逐字编码，只核事件 INSERT + 含 RAISE。

归一形式明确为「小写 + 压缩空白」；结构判据以 `CAPABILITIES` 显式字段呈现，可审阅，不再逐条扩充常量黑名单。探针扩至 28 用例（新增 X05～X09 五个负例）全过。

## 四轮核验修正（M13 字符串字面量与谓词大小写 X10/X11，2026-10-24）

C 四轮独立复核（本地 abda94e，未推送）确认 cece332 的 X01～X09 全部通过，但仍发现两项有效定义缺口：X10 同名 `BEFORE DELETE` 触发器体仅为 `SELECT 'RAISE';`（字符串字面量，无真实 RAISE 调用）被接受；X11 唯一索引谓词被改成 `status IN ('PREPARED','COMMITTED')`，整体转小写后被误认作规范谓词 `status IN ('prepared','committed')`。C 要求核实真实有效保护定义、保留字符串字面量语义，并补「有效原 schema 控制组」。A 修正：

- 真实 RAISE 判定：新增 `stripTrivia` 去 SQL 注释与字符串字面量（字符串内容替换为 `q+q` 空占位），RAISE 判据改为 `/\bRAISE\s*\(/i` 命中 `stripTrivia` 结果——`SELECT 'RAISE'` 的字符串字面量被清空，不再误命中（X10）。
- 字符串字面量语义保留：`normalizeSql` 改为逐字符归一，仅字符串/引号标识符之外小写，字符串字面量内容原样保留（小写不进入引号内），因此 `'PREPARED'` ≠ `'prepared'`（X11）。
- CHECK 判据同步用 `stripTrivia`（去注释与字符串）后再匹配表原文，替代原 `stripComments`（去注释）；结构判据其余不变。

探针扩至 30 用例（新增 X10/X11 两个负例），并新增「有效原 schema 控制组」（enforcement）两项：c-v7 上 `agent_tool_step_no_delete` 实际拒绝 DELETE、c-v6 上 `agent_write_once` 实际拒绝重复 `prepared` 插入——证明原保护真实生效，而非仅识别通过。

## 五轮核验修正（M13 错表/不可达 RAISE 与旧账本未知/重复登记 Y01～Y03、M09-L01/L02，2026-10-25）

C 在固定提交 41f0cdc 上独立复核，确认 X01～X11 11/11 通过、有效原 schema 控制组真实拒绝；但 107 样本扩展矩阵发现 5 项新失败：M09-L01（未知 version=99 被接受）、M09-L02（无唯一约束旧账本重复 version 被接受）、M13-Y01（`CASE WHEN 0 THEN RAISE(...)` 不可达 RAISE 被接受）、M13-Y02（同名触发器挂到错表 agent_run 被接受）、M13-Y03（同名唯一索引建在旁表 synthetic_index_target 被接受）。C 要求拒绝必须发生在升级/写入前，并保留 X01～X11、九段历史 SQL 指纹、正向升级与旧证据。A 逐项修正：

- 真实 RAISE 必须为直接保护体：RAISE 判据从 `/\bRAISE\s*\(/i` 收紧为 `/\bSELECT\s+RAISE\s*\(/i` 命中 `stripTrivia` 结果——`CASE WHEN 0 THEN RAISE(...)` 的 `SELECT CASE` 前缀不命中（M13-Y01）；九段规范保护体均为直接 `SELECT RAISE(...)` 形式，不受影响。
- 触发器/索引目标表核对：`TriggerRequirement`/`IndexRequirement` 各新增 `table`（规范目标表），`identifyLineage` 从 sqlite_master `tbl_name` 收集 `triggerTable`/`indexTable`，`capabilityStatus` 核对 `triggerTable.get(name)===table` 与 `indexTable.get(name)===table`——同名对象挂到错表（agent_run）或旁表索引（synthetic_index_target）即 partial/tampered（M13-Y02/Y03）。
- 旧账本未知登记拒绝：`verifyLegacyLedger` 对 `legacyMap` 无映射的 version 直接抛 tampered，不再 `continue` 静默忽略（M09-L01）。
- 旧账本重复身份拒绝：`verifyLegacyLedger` 以 `seenVersions` 集合拒绝重复 version，不静默去重/改写历史账本（M09-L02）。
