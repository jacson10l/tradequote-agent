# 0006-M1契约基础与实施边界

## 背景

首个工作区纵向切片只有两个 patch schema，setQuantity 的 quantity/unit 形状与规划 Quantity.value/unitId 不一致；运行事件 payload 尚无可执行约束。用户要求继续推进 M1，三人 T00 尚未实际评审，不能把 schema 增量等同完整报价或真实模型完成。

## 决定

当前按设计草案补九种受限补丁及版本修订输入，统一嵌套 Quantity；审批绑定与补丁 schema 分离，不导出到模型补丁工具。金额/数量为 decimal 字符串，未知由五态 Fact 表达，来源位置与证据独立。所有 patch 和事件 payload 使用 strictObject；公共错误码复用同一枚举。测试/mock 同步，IPC allowlist 保持现有工作区三个方法。

应用层金额、单位目录、来源有效性、权限与生命周期仍需 M2～M4 服务验证；本次只建立可评审契约基础，不发布“模型已批准”“已保存报价”之类假结果。

## 替代方案

继续保留扁平 quantity/unit 会让后续 renderer/Agent 各自产生不同 DTO；接受任意 JSON Patch 或 payload:unknown 无法在边界拒绝 total/approval/actor 注入；为所有计划用例返回 fake success 会掩盖服务未实现。因此先同步已有夹具与拒绝测试，保留未实现用例的真实边界。

## 后果

旧 setQuantity 输入将被拒绝；目前没有持久报价数据、外部发布接口或生产调用方，变化仅影响初始 schema 测试与 mock，已同时迁移。T00 人工评审仍需要决定金额精度/配置目录、更多查询命令和业务字段，不以本 ADR 代签。

## 回滚方式

可回退本次契约文件、mock 与测试到初始化基线 7c5a2eb；不变更或降级数据库迁移，不删除工作区数据。未来已保存报价/外部接口采用后，任何破坏变更须新增 schema 版本与迁移评估。
