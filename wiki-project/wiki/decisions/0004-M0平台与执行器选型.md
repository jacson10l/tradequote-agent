# 0004-M0平台与执行器选型

## 背景

此前 Harness 在独立 Node 进程通过，本轮 Electron 44.9.2 下真实启动失败，native loader 明确拒绝该 Node/V8 指纹。用户允许实测后替换，并要求先推进开发、最终安装验收暂缓。

## 决定

默认采用 Electron 44.9.2 与隔离的最小工具执行器、DeepSeek HTTP Provider；Harness 0.2.1-rc.2 留作 dev 候选，不进生产依赖。保留 SQLite/better-sqlite3/Drizzle 和四类解析基线；PDF 默认 printToPDF，独立沙箱、禁脚本、阻外网、嵌入合法字体。模型设置由 UI 输入 Key，系统加密可用才持久化。

## 替代方案

不直接降级 Electron 以迁就 Harness 的有限指纹；自带 Node sidecar 能隔离 ABI，但增加分发/更新/进程管理成本，目前未验证；Fork Harness 内核成本高。react-pdf 已真实渲染长表，亦存在阿拉伯文本回读问题，没有证据表明值得再维护一套模板。

## 后果

最小执行器的流式、持久化运行恢复、评估与预算需自行补齐。探针通过不等于全量业务实现；T00 三人评审、真实模型、RTL 精确文本与 Windows/签名安装仍未通过。用户暂缓安装验收调整推进顺序，保留发布前关卡，不伪造通过。

## 回滚方式

保持 AgentRuntime/ModelProvider 端口；当 Harness 新版或独立 Node sidecar 在目标 Electron、打包与工具隔离上通过同一探针，可通过新 ADR 替换 adapter。文件解析/PDF 同样经 ports 替换，历史事实快照和审批绑定不依赖引擎。
