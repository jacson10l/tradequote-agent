# 0003-工程Wiki维护基线

## 背景

原执行把机械索引与门禁推迟到 M1，进入 M0 已产生源码仍未同步补齐，偏离用户规范。本轮按现有源码增量建设，不改根规则或重新脚手架。

## 决定

使用 Node 标准库维护确定性代码清单、hash 快照、覆盖矩阵、运行时清单和 inventory JSON。显式 ingest 固定基线；--check/lint 全程只读。每个纳管文件按职责手动映射；未分类新文件失败。所有符号链接不跟随，读取前排除敏感路径。Wiki 不递归充当应用源码，脚本/配置另存指纹并做反向测试。

## 替代方案

只建 Markdown 目录无法检查漂移；按当前时间/HEAD 每次重建会导致无内容变化的提交永久失败；自动把文件全部映射到“其他”不能说明责任。没有引入模型服务、向量库或新应用依赖。

## 后果

维护者新增模块时必须阅读、分类并更新语义页。schema 采用明确的小型 YAML 子集；外部原件不改格式，示例链接不当作工程导航。自动检查只能证明结构/路径/内容指纹，无法证明语义或完整安全性；证据等级保持明确。

## 回滚方式

若需要成熟 YAML/Markdown 解析器，可在保持 CLI 和负向用例的前提替换内部实现。生成物可按固定基线重建；不得用删除检查规则或手改快照掩盖失败。跨项目迁移保留原采集基线，显式 ingest 才变更其元数据。
