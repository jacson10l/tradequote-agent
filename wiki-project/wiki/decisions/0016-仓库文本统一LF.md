# 仓库文本统一 LF

## 背景

A 报告四份归档 ARCHIVE_HASH_MISMATCH，干净 Windows 检出还可能出现 GENERATED_DRIFT。共同基线没有 .gitattributes，core.autocrlf=true 会改变文本工作区字节；本机核对四份 LF 归档匹配原基线，CRLF 不匹配。属于公共工程配置缺失，由 C 承担独立修复，不将其归因于 A01b 内容变更。

## 决定

采用方案 A：默认 text=auto eol=lf，已知源码/配置/归档文本显式 text eol=lf，二进制 -text；执行 git add --renormalize . 并重新生成机械清单，保留原归档与哈希基线。pnpm check 先运行只读换行门禁，维护工具增加 .gitattributes 的 P0 同步识别。交付目标 codex/m1-foundation，非作者评审后再合入，Actions 保持停用。

## 替代方案

按 CRLF 重算哈希会使 LF 环境失败；豁免四份归档削弱完整性；校验器内部归一化会改变原字节校验含义，均不采用。仅要求成员关闭全局 autocrlf 无法提供随仓库分发的统一约束。

## 后果

已有 LF 索引可以不产生任何纯换行提交，不预设大规模 blame 噪声。已存在的 CRLF 工作区不会因 renormalize 自动重写，成员需先保存未提交/未推送工作，再在包含修复的新 clone 检出任务分支。归档和二进制逐字节保持；业务接口、金额、数据库和模型无变化。macOS 上 Git 配置模拟只验证检出机制，Windows 实机仍未验证/后置。

## 回滚方式

若资源被错误识别，应先添加准确的 -text 例外并复核字节，不改批准哈希。确需撤回策略时以新的独立 PR 同步撤回门禁接线与相关文档、重新生成并验证；不重写团队历史，不删除验证证据。撤回会重新暴露跨平台换行风险。
