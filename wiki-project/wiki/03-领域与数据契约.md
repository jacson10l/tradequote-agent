# 领域与数据契约

这是三人开工时要转为 Zod schema、数据库迁移和契约测试的 v1 设计。示例是规范草案，不是仓库中已存在的 TypeScript 实现。公共契约由 B 主维护，A 审核存储，C 审核工具与 IPC 可表达性。

## 基础类型

| 类型 | v1 约定 |
|---|---|
| ID | UUID 字符串，跨平台/未来服务器保持稳定；不能以数组下标或 SKU 代替实体身份 |
| DecimalString | 普通十进制字符串，如 `"12.500000"`；拒绝 NaN/Infinity、货币符号、千位符、科学计数法；外部原文另存 |
| Money | `{ amount: DecimalString, currency: string }`；币种必须存在于已确认的币种目录 |
| Quantity | `{ value: DecimalString, unitId: string }`；单位维度如 count/mass/area/length；单位由注册表定义 |
| Locale | BCP 47 标识；自然语言名称须解析并展示确认结果；不得限制为 en/de 两种 |
| Time | UTC ISO 8601；报价有效期等当地商业日期另保存 `YYYY-MM-DD`、时区与含义 |
| Version | 整数递增的业务版本；与 schemaVersion、模型版本、数据库 migration 版本分开 |
| Unknown | 显式状态及原因；缺失、零、不适用是不同语义 |
| Evidence | 来源版本、位置、摘录哈希；用户手工确认是单独证据类型，有操作者和时间 |

```ts
type Fact<T> =
  | { status: "confirmed"; value: T; evidenceIds: string[] }
  | { status: "proposed"; value: T; evidenceIds: string[] }
  | { status: "missing"; reason: string }
  | { status: "conflict"; candidateEvidenceIds: string[]; reason: string }
  | { status: "not_applicable"; reason: string };

type SourceLocation =
  | { kind: "sheet"; sheet: string; cellRange: string }
  | { kind: "csv"; row: number; columns: string[] }
  | { kind: "pdf"; page: number; textSpanId: string; bbox?: number[] }
  | { kind: "docx"; paragraphId?: string; tableId?: string; cell?: string }
  | { kind: "text"; start: number; end: number };
```

位置以原始版本为基准，行/页从 1 开始。DOCX 不制造依赖渲染器的“固定页码”；PDF 文本按页保存稳定 span ID。对于抽取失败的字段，不能凭模型猜测补一个位置。

## 实体、关系与所有权

所有持久化记录带 `workspaceId`。表名为建议名，M1 转迁移时统一 snake_case。

| 聚合/表 | 必需数据 | 所有者与约束 |
|---|---|---|
| Workspace / ActorProfile | 名称、演示标记；本地操作者名与岗位 | C；本地角色切换不能证明真实身份 |
| Customer | 名称、语言偏好、已确认交易模板引用 | B；首版轻量客户，不建设完整 CRM |
| SourceDocument | id、hash、storageKey、文件类型、原名、导入人、来源说明 | A；原件不可变，同 hash 可复用文件但保留导入记录 |
| ImportBatch / ImportRow | sourceId、mappingVersion、提取结果、错误、确认状态 | A；staging 与已发布数据分开 |
| CategorySchemaRevision | 属性键、类型、枚举、是否必填、单位维度、展示顺序 | A；版本化，商品引用确定版本 |
| Product / ProductRevision | SKU、名称、schemaRevisionId、typedAttributes、销售单位、MOQ、来源 | A；`(workspaceId, sku)` 唯一，修改创建 revision |
| PriceRevision | productRevisionId、priceKind、币种、单位、tiers、有效区间、条件、来源 | A；priceKind 为 sales 或 purchase；同条件的数量区间不重叠 |
| UnitDefinition / UnitConversion | 维度、精度、from/to、ratio、适用商品、来源版本 | A；包装箱→件可为商品专属；禁止无依据的 kg→件 |
| PricingPolicyRevision / FXSnapshot | mode、margin、discount、feePolicy、rounding；汇率方向与时间 | B；批准的配置，引用快照，人工汇率不标为实时 |
| KnowledgeEntry / KnowledgeRevision | Markdown、原件位置、适用品类/市场、有效期、状态、审核人 | A；只检索已发布且适用版本；模型产出不是自身事实证据 |
| RuleRevision / GlossaryRevision / TemplateRevision | 规则类型/条件/动作、术语对、语言/场景模板、来源 | A 发布通道；B 定义检查语义；C 定义生成模板接口 |
| Inquiry / InquiryRevision | 客户、原文、来源语言、场景、提取字段、缺项、引用 | B；保留每次结构化需求版本 |
| Quote | id、number、customerId、currentRevisionId、aggregateVersion、归档标记 | B；revision 内容不可直接更新 |
| QuoteRevision / QuoteLine | parentId、seq、冻结快照、计算轨迹、输入版本、contentHash | B；`(quoteId, seq)` 唯一；lineId 跨版本保持稳定 |
| RuleCheck | checkId、category、revisionId、artifactId/hash（产出检查）、ruleRevisionId、适用性、结果、severity、fieldPath/contentBlockId、原因、建议、证据 | B；风险标记与文本批注共享同一结果；绑定快照/产出，检查引擎版本可追溯 |
| ReviewTask / TaskEvent | quote/revision、字段、岗位、问题、证据、解决结果 | B；不得跨版本误用旧确认 |
| OutputArtifact / OutputBundle | revisionId、语言、场景、platform/localization profile 与 template/terms 版本、检查结果引用、hash、文件键 | B；正文/PDF 都不可变；bundle 固定要审核的产出列表 |
| Approval / LifecycleEvent | revision/contentHash/bundleHash、操作者、结果、说明、时间 | B；追加事件；不修改旧审批来“沿用”到新内容 |
| Citation | consumerType/id、sourceRevisionId、location、factPath | A 维护来源索引；业务用例提交自己的引用记录 |
| AgentRun / ToolCall / RunEvent | 输入版本、执行器/模型/prompt/schema 版本、状态、关联 revision、usage | C 定义，A 持久化适配；不储存明文凭据 |
| IdempotencyRecord / Job / Outbox | key、payloadHash、结果引用；作业状态；待发布事件 | A 实现，应用服务使用同一事务 |

一个 SourceDocument 可支持多个知识/商品版本；一个报价版本引用多个来源；引用关系不能仅藏在聊天文本。知识 Markdown 内容存为不可变 artifact，SQLite 管发布与引用；索引是可重建副本。

已引用实体采用停用/归档，不物理删除被快照引用的证据。清理历史文件必须先检查引用；原件丢失作为错误显示，不能装作可追溯。

## 平台与本地化配置（待实现设计）

为 [[参赛要求对齐与验收]] 的 AC-17 补充 PlatformProfileRevision 与 LocalizationProfileRevision。前者记录业务平台/场景、规则版本引用、必需内容结构与企业风格建议；后者记录 locale、目标市场、受众/已确认客户偏好、称呼与语气、术语、日期/单位展示约定及来源。强制平台规则与风格建议分开，不把国家标签推导为个人文化偏好。配置由 A 的人工发布通道保存不可变版本，B 维护规则与检查，C 使用模板生成。

配置来源需保存原件/URL、摘录位置、取得日期、适用范围、有效性及确认人。演示配置只是可替换的样本组合，不限制平台、品类、市场或语言。T19/T24 先准备配置与正反样本，T00/T11 评审字段后才扩展 executable schema、调用方、mock 和迁移；本轮没有新增运行服务。

产出保存实际使用的配置版本与引用，平台/语言/模板变更生成新 artifact/bundle 并重新检查，不改旧产出或沿用审批。变更目标市场等业务事实时必须创建新报价版本并检查适用规则，不能仅换文案配置。风险标记与文本批注均从 RuleCheck 投影；报价检查绑定 revision，文案检查同时绑定 artifact/hash，人工确认或修订后保留旧检查历史。模型语义检查仅作辅助，来源不足为待核实，人工语言复核独立记录。

## 跨品类与价格档位

固定核心字段负责 SKU、单位、数量、价格、版本和证据；类别 schema 负责诸如成分、厚度、尺寸、等级等属性。属性必须有类型和单位，不能全部退化成无约束字符串。

价格档位采用 `[minInclusive, maxExclusive)`，最后一档 `maxExclusive=null`。选择档位前，数量转换到价目表单位；转换比例也保存快照。币种、有效期、客户条件或规格条件存在多个同优先级候选时返回冲突，由用户选择，禁止隐式“取最新/最低”。

MVP 定价策略提供有类型的算子：数量档位、单位换算、固定/按量费用、折扣、汇率、目标毛利。新增普通品类通过属性和策略配置；未知行业公式返回“需要配置”，后续以实现 `PricingStrategy` 的受测模块扩展，不允许 Agent 动态执行任意 JS 公式。

## 报价快照

一个 QuoteRevision 至少冻结：

1. InquiryRevision、客户与交易主体信息、目标市场/场景。
2. 每行 ProductRevision、选中 PriceRevision、规格、数量与单位转换。
3. 定价策略、汇率、费用、折扣、精度/舍入及确定性计算轨迹。
4. 付款、贸易条件、指定地点、交期起算条件、有效期；未确认值保留状态。
5. 规则集、知识版本引用及来源、输出默认配置版本；原件 hash。具体语言产出另在 artifact 中冻结其实际术语和模板版本。
6. 变更原因、actor、runId、父版本和 schemaVersion。

快照序列化采用固定字段排序与规范化 decimal，计算 SHA-256 `contentHash`。保存后不修改内容。后台可更新单据当前指针与追加状态事件，但不能重写旧 revision JSON。当前指针变更、提交审核、批准、驳回和标记发送均在事务内比较并递增 Quote.aggregateVersion，避免审核动作与编辑互相覆盖。

修改数量默认保留当前来源版本，在该价目表重新选档；显式选择新价格/新资料才换依据。若当前来源已经失效，草稿标记待复核，审核必须处理。语言/场景变化只生成绑定同一事实版本的新产出，不改数量金额。

## 状态和审批

不要将“资料不完整”和“已经审核”压成同一个状态字段：

- 工作就绪度由检查结果推导：`needs_clarification | needs_internal_confirmation | ready_for_review`。
- 版本生命周期由事件推导：`draft | in_review | approved | rejected | sent`。
- 当前版本是 Quote 的指针；历史版本显示“非当前版本”，同时保留曾审核/曾发送事实。
- AgentRun 有独立状态，模型失败不把已保存报价变成失败单据。

| 操作 | 前置条件 | 结果 |
|---|---|---|
| 保存新草稿 | expectedAggregateVersion 匹配；patch 合法 | 新 revision＋计算/检查＋任务＋outbox 原子提交 |
| 提交审核 | 当前 revision；无必填缺口、事实冲突、block/pending 关键检查 | 保存待审核事件与产出 bundle |
| 人工批准 | 人工会话通道；当前 revision/contentHash/bundleHash 匹配；重新检查有效性 | 新 Approval；审批只覆盖指定 bundle |
| 驳回 | 人工操作、指定版本 | 记录原因；修正创建新版本 |
| 导出正式 PDF | 对应 artifact 的 bundle 已批准，文件哈希匹配 | 导出原有或确定性重渲染的产出；不标发送 |
| 导出草稿 | 已保存 revision | 显著标记草稿、未确认字段和版本 |
| 新语言/重生成正文 | 同 revision 可创建新 artifact/bundle | 新 bundle 未批准，不借旧审批导出正式版 |
| 恢复历史 | 选择旧 revision，当前版本并发检查 | 复制其业务输入生成新 revision；重检时效，不复制审批 |
| 标记发送 | 人工确认具体批准 bundle | 追加发送记录；首版没有邮件发送能力 |

普通 warning 可由人工备注后接受；金额不一致、事实冲突、关键未知项和未完成适用性判断不能用一个“忽略全部”按钮放行。例外若确有业务依据，先发布例外配置/确认记录，再产生新版本与复核。

## 金额口径

内部十进制精度基线为 28 位有效数字；数量/单位价格保存至配置允许的小数位。币种表定义结算小数位，舍入模式基线 `ROUND_HALF_UP`。策略与精度随版本冻结，测试防止任意中间舍入。

价目表模式：

```text
q = 转换到报价单位后的数量
u = 适用价档的销售单价
lineNet = roundCurrency(q × u × (1 - lineDiscount))
subtotal = Σ lineNet
total = subtotal + Σ 已确认对外费用金额
```

首版折扣作用于行商品金额，不默认作用于运费/税费。整单折扣若配置，先按行折扣后金额比例分摊，以最小货币单位分配余数，固定 lineId 排序打破并列，保证行金额和总额一致。负数量/负售价拒绝；贷项单不属于首版。

成本模式：

```text
fx = 人民币 / 1 美元（示例方向，实际结构保存 from/to/operation）
unitCostUSD = unitCostCNY / fx
allocatedUnitCost = 单位采购成本 + 单位费用 + 已分摊整单成本 / q
quotedUnitPrice = roundUnitPrice(allocatedUnitCost / (1 - targetMargin))
lineNet = roundCurrency(q × quotedUnitPrice × (1 - lineDiscount))
actualMargin = (纳入毛利的收入 - 纳入毛利的成本) / 纳入毛利的收入
```

`0 ≤ targetMargin < 1`，收入为零时毛利率为“不可计算”；目标毛利不是成本加价率。折扣后重新检查实际毛利，不能继续展示目标值为实得值。单价舍入后用该展示单价计算行金额，防止 PDF 上数量乘单价对不上总额。

整单成本按已确认的直接成本比例分摊，余数有确定性规则；直接成本总和为零时要求人工分摊，不凭不同维度的数量相加分摊。每项费用明确 `cost|sale|both`、`per_unit|per_order`、是否计入毛利、币种、分摊规则，避免成本核价后又对同一成本重复加价。

税费/运费明确“已包含、另列、未纳入、待确认”，每单显示计算覆盖范围。禁止跨币种直接求和；汇率必须指定来源和时间。未知成本可保存不完整草稿，但总额不得把未知费用当零且显示“完整报价”。

例：采购成本 CNY 72/件，汇率 7.2 CNY/USD，无其他成本，目标毛利 20%，得到 USD 10 成本与 USD 12.50 售价；1,500 件总额 USD 18,750，毛利率 20%。该例仅验证计算，不代表真实商品价格。

## 事务、幂等与迁移

- 幂等键按 `(workspaceId, commandName, idempotencyKey)` 唯一，保存请求 hash 与结果 ID；同键同参数返回原结果，同键异参返回冲突。
- 事务前完成模型调用和大文件处理；事务内检查 expectedAggregateVersion，写 revision/line/check/task/citation/outbox/idempotency，再更新当前指针。禁止提交一半的新版本。
- ReviewTask 用 `(revisionId, ruleId, fieldPath, issueCode)` 去重；旧任务保留，当前 UI 不把旧任务误计为未完成。
- 文件先写临时区、算 hash、原子改名；数据库只引用完成的文件。失败孤儿文件由可重入清理任务处理，不删除仍被引用文件。
- migration 顺序由 A 维护，已合并 migration 不改写；升级前一致性备份，失败保持旧库可恢复。SQLite decimal 存 TEXT，由业务计算，不用 SQLite 浮点 SUM 作为金额事实源。
