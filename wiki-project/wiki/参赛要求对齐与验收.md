# 参赛要求对齐与验收

本页是参赛范围与验收的现行解释，依据用户提供的单页截图及其转录，不声称已取得完整赛规。截图保存在 [原图](../raw/inputs/2026-10-21-参赛任务截图.png)，逐字内容见 [转录](../raw/inputs/2026-10-21-参赛任务转录.md)。原始方案保留不改；与本页冲突的旧赛事解读由本页取代。当前正式实现已有工作区与手工报价 V1，详见 [[M2真实报价V1]]；六项参赛整体验收仍未完成，文档对齐不代表功能通过。

## 要求边界与纠正

| 类别 | 本次解释与项目决定 |
|---|---|
| 截图硬要求 | 明确业务场景；可用 AI 应用；两种目标语言或两类角色/场景；商务与文化适配；至少两轮对话迭代；目标平台风格与规则适配；至少两类校验、两种反馈；稳定演示两个相关工作流 |
| 二选一关系 | “两种语言”与“两类角色/场景”不是同时必须。项目选择英语、德语两种目标语言作为首批参赛验收路径；RFQ/邮件及中文内部任务保留为产品设计，不增加赛事硬门槛 |
| 平台数量 | 没有“至少两个电商平台”的要求；阿里国际站/Amazon/TikTok 是风格示例，不要求全部实现。旧原始方案第 16 节的“至少两个平台或场景”不是本截图原文 |
| 三种平台含义 | AI 构建平台不限；目标业务平台需要内容适配；macOS/Windows 是项目运行平台。三者分别验收，不能相互替代 |
| 鼓励/建议/可选 | 批量生成是鼓励项；数据与知识调用是建议项；多岗位输出是可选项。项目仍保留知识来源和内部任务，因为它们支撑报价可靠性 |
| 项目自身要求 | 双平台安装、跨品类三组样本、四类导入、两种定价、CJK/RTL 排版、不可变快照、审批与故障恢复继续有效；不是从截图新增推导出的赛事要求 |
| 未覆盖信息 | 海报尺寸、演讲时长、提交格式、评分权重、原创性细则均不由此截图确定；取得完整规则后另行核验 |

无需增加平台 API 连接、自动外发、多租户或多个自主 Agent 来满足本页任务。批量队列继续后置，不删原有项目 P0，不把阶段切片完成称为完整 MVP。

## 场景与演示配置

目标用户：有商品与价格资料、通过 RFQ/邮件接询盘的中小出口企业业务员；采购确认未知费用与交期，主管审核对外承诺。触发为粘贴询盘或买家变更；处理为检索已发布资料、澄清、确定性核价、规则检查、保存版本与生成产出；输出为目标语言回复/报价 PDF、差异和内部任务。价值以减少遗漏、保持事实一致和可追溯为主；记录操作时间/修正次数，不虚构效率百分比。

T19 的起始演示候选为“阿里国际站 RFQ → 正式邮件报价”，首批输出英语与德语；沿用旧资料中的成人定制服装/德国仅作为样本候选。平台、市场、品类及资料适用性由 T19 核对后形成一份明确配置；当前没有真实平台规则验证或业务专家确认。资料不足可替换候选，不能用合成规则声称符合真实平台/目标国规则。

演示配置须记录目标用户、品类、目标市场、业务平台、两个场景、语言、参与岗位、输入文件及 hash、规则/术语/模板版本、资料确认人和证据状态。配置可替换，产品仍跨品类并允许其他目标语言。

## 六项逐项验收

| 编号 | 现场可观察的通过标准 | 证据与任务 |
|---|---|---|
| C-01 场景 | 能用同一案例解释用户、平台或市场、痛点、触发、处理、输出及岗位；演示配置有具体值 | 场景卡与样本清单；T19/T20 |
| C-02 AI 应用 | 在正式 Electron 应用输入业务请求，真实模型调用已接入业务工具，界面显示真实结果和失败；角色/任务/知识范围可核对 | 输入、run/tool 记录、配置版本；T40/T41/T42 |
| C-03 产出与迭代 | 中文输入后生成英德业务产出；完成初稿 V1 后两轮自然语言变更并保存 V2/V3；每轮看到受影响字段、重新计算/检查和新产出，旧版不变；按下述本地化标准通过 | 三版本、两轮对话、语言复核与 artifact hash；AC-04/08/10/17，T31/T42/T43/T53 |
| C-04 平台适配 | 选定业务平台的产出采用已确认的平台规则与模板；RFQ 和正式邮件的信息组织有实质区别；至少一个违规/缺依据样例得到反馈，修正后重新检查 | 平台来源、适用性、模板版本、前后产出；AC-17，T24/T32/T43 |
| C-05 校验反馈 | 至少覆盖合同条款与有资料支持的目标市场规则两类；平台规则另纳入适配检查；同一问题同时提供风险标记和文本批注，能追到字段/文本、依据、建议；修正后重新检查 | 每类至少一例问题与处理结果、双反馈截图、check IDs；AC-07，T32/T53 |
| C-06 可重复互动 | 工作流一“询盘→可审核报价”，工作流二“买家变更→新版本、风险说明和采购/审核任务”真实运行；两条流可共享单据但各有触发与产出；隔离重置后连续完成 5 次演练（次数为项目标准） | 重置步骤、操作记录、run/revision/artifact IDs；T50/T51/T52/T63 |

创建工作区/重命名不是参赛两条业务工作流；初稿加一次修改也不是两轮迭代；两个岗位标签不是两个角色的实际业务产出。RFQ 与邮件是输出场景，不能代替两条相关工作流的验收。

## 平台与文化适配的可检验标准

平台适配配置分开记录“有来源的平台强制规则”和“企业/商务风格建议”。来源含 URL 或导入原件、摘录位置、取得日期、适用市场/场景、有效性及确认人；当前不填写未经核验的具体平台规则。无来源、过期、冲突或适用性不明时显示待核实，不能把模型意见当作规则或显示已通过。

| 维度 | 通过标准 | 反例/失败信号 |
|---|---|---|
| 内容结构 | RFQ 围绕需求匹配、已知报价条件、关键澄清与下一步；正式邮件有主题/称呼、完整报价条件、有效期、附件说明与后续动作；二者源于同一事实 | 相同文本只换标题；缺项被自动补成承诺 |
| 平台规则 | 对所选平台适用规则逐条给出来源、命中位置与处理结果；导出前复查适用性 | 只写“符合平台规则”；虚构禁词/字数上限；用邮件模板证明 RFQ 平台合规 |
| 商务语气与文化 | 按客户已知偏好、已确认模板/术语选择称呼、礼貌程度、请求和拒绝方式；表达清楚且无无依据的文化刻板推断 | 逐字翻译、语气不合场景、根据国籍臆测个人偏好或编造认证/承诺 |
| 本地格式与术语 | 术语一致；日期、数字、币种、单位展示符合所选 locale 且含义无歧义；任何业务单位/币种换算走确定性业务模块 | 排版/小数符号改变数值；换语言后 SKU、交期条件或金额漂移 |
| 事实保护 | SKU、规格、数量、金额、日期与承诺来自冻结快照；未知项保持未知；目标语言保留限定条件 | 为使文案自然而承诺未确认交期；删除风险限定；泄露采购成本 |

T24/T43 至少准备同一事实的两种语言与 RFQ/邮件结构对照，附逐项适配理由；T53 用正常、机器直译式不合适表达、无依据承诺、规则过期/冲突样例复核。语言/业务复核人记录姓名或角色、结果与修改理由；模型自评与字体渲染通过不能代替人工语义评估。评分与通过阈值见 [[06-测试与交付]]。

## 两类校验与两种反馈

“校验类型”“反馈方式”“严重程度”分别计数。两种红/黄标记只是同一种反馈；两条文字提示也只是文本方式。首版固定采用风险标记＋文本批注，版本可视化对比为补充，不要求语音。

每条 RuleCheck/Issue 关联同一个 checkId、category、报价 revision；产出检查另绑 artifact ID/hash，并含 ruleRevisionId、证据、fieldPath 或内容块位置、结果、严重程度、原因及建议。风险标记显示文字状态与类型并可定位；文本批注解释哪里不符、依据是什么、如何处理。两者必须来自同一检查结果，不能出现标记已通过而批注仍阻断。

示例仅作测试输入：缺少付款条款触发合同检查；某产品缺少已发布目标市场规则要求的证明触发待核实；不把此例写成真实法律结论。每类至少覆盖问题→双反馈→人工补充证据或修改→新版本/新产出→重检。旧检查与旧审批保留历史归属，不因关掉标记而消失；关键待核实/阻断仍禁止定稿。界面表单必填校验不能冒充第二类业务规则。
