A 接收 C 复验报告（初轮 `8de82ce`、最新 `988e69f`，其原始证据见 C 分支 `raw/c-a24-reverify.json`、`raw/c-a24-event-evidence.json`），逐项判定两项待修项归属，并交付第一项修复。固定基线 `24c3eae96bf002ee0f6898733fff089c617f4162`，生产修复落于 `2a61261`、反例回归落于 `fdd571a`（均已推送 `origin/codex/a01e-p3-fixes`，远端回读一致）。

## 第一项：快照绑定校验 —— A 已修复 ✅

**C 复现的反例**：对两条 open 问题取全量快照，再取 `states=[resolved]` 查询的 queryHash，用「前一个 snapshotId 配后一个 queryHash + 真实 afterIssueId」续页，服务 `ok` 并返回 open 问题，绕过 resolved 过滤。

**根因**：`getMaintenance` 只比较 `请求 cursor.queryHash` 与当前查询 hash（可被客户端把两者拼一致绕过）；`readMaintenanceSnapshot` 只按 snapshotId 加载 issues_json，不核对数据库保存的 `workspace_id`/`query_hash`。

**修复**（`2a61261`）：`readMaintenanceSnapshot` 读回 `workspace_id`/`query_hash`/`issues_json`，`getMaintenance` 续页分支核对 `snapshot.workspaceId === workspaceId && snapshot.queryHash === queryHash`，不一致返回 `REVISION_CONFLICT`；快照不存在/损坏统一 `REVISION_CONFLICT`，不再静默返回其它过滤结果或伪造空终页。

**反例回归**（`fdd571a`，测试 `A01e-2c`）：精确复刻 C 的伪造换绑场景，断言必须 `REVISION_CONFLICT`；另附合法续页正向控制，确认修复未误伤正常分页。A 临时禁用核对验证反例由绿转红、恢复后转绿，证明该核对是唯一关卡。

**验证**：wiki-store 28/28（原 27 + A01e-2c）、`pnpm typecheck` 退出 0、check-wiki-sync（base `2a61261`）passed、lint-wiki 通过（仅 4 个预存在 Windows CRLF `ARCHIVE_HASH_MISMATCH` 保留，非本轮引入）。

## 第二项：事件证据解析与资格核验 —— 归属 B，A 不越界单方面实现 ⚠️

**C 实测**（`raw/c-a24-event-evidence.json`）：完整撤回事件持久化于幂等回执、outbox 引用业务事件 ID、不同 requestId/宿主 now 的回放控制通过（1 控制通过）；但把返回的 `eventId` 作为对应来源维护项的 resolve 证据得到 `NOT_FOUND`，处理无部分写入（1 失败）。

**技术根因**（A 核对，供 B 决策的精准输入）：
1. `emit()` 写 outbox 时 `event_id = randomUUID()`，是独立**投递 ID**，与业务事件 `eventId`（`source.withdraw` 内另一次 `randomUUID()`）是**两个不同 UUID**。
2. 业务 `eventId` 未持久化到任何可被 `readEvidenceFact` 查询的表（outbox 的 event_id 是投递 ID；idempotency 表存整条 result JSON，不按 eventId 索引）。
3. `readEvidenceFact` 白名单现有 6 类（sourceRevision/wikiRevision/lintReceipt/consumption/impactReport/indexRebuild），**无「事件」读取分支**；`evidenceBindsTarget` 也无事件的「绑定目标与版本」资格逻辑。

**责任边界**：C 报告原文明确「执行资格政策仍由 B 明确」「仅统一两个 ID 不会自动修复 readEvidenceFact 缺事件读取分支」「B 需逐方法验证，不能把 10 个 emit 一概外推为同一缺陷」。因此事件是否属于 `resolveMaintenance` 的已存执行证据，是 B 的契约/资格政策决策，非 A 可单方面实现——方向可能错（仅统一 ID 不解决问题）。

**待 B 明确**：
- 哪些事件类型（10 个 emit 中的哪些）具备「解决事实」资格；
- 事件需持久化的可查询表结构（workspace_id + 固定目标/版本 + 操作类型）；
- 事件绑定问题目标的资格规则。

**A 待命**：B 明确资格政策后，A 落地「事件持久化表 + `readEvidenceFact` 事件分支 + `evidenceBindsTarget` 事件绑定 + 回归」。
